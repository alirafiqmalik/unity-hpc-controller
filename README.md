# unity-hpc

A local Claude Code plugin (in the `phd-agentic-tools` marketplace) that packages the Unity HPC cluster workflow as coordinated skills, an MCP server, utility scripts, and autonomous agents. Skills invoke as `/unity-hpc:<skill>`.

## Install

This plugin lives in the `phd-agentic-tools` marketplace at the repo root.
Add the marketplace (`/plugin` → Add Marketplace, or):

```bash
/plugin marketplace add /home/ahm/Desktop/project/Research/tools/hpc-experiment-workflow
/plugin install unity-hpc@phd-agentic-tools
```

For local development, load the plugin directly without installing — changes
take effect on `/reload-plugins`, with no cache copy to keep in sync:

```bash
claude --plugin-dir /home/ahm/Desktop/project/Research/tools/hpc-experiment-workflow/plugins/unity-hpc
```

A `--plugin-dir` copy takes precedence over the installed one for that session,
so you can test changes without uninstalling.

Skills, agents, and the `unity-hpc` MCP server register automatically — no
`claude_desktop_config.json` edit needed. The MCP server runs via `uv`, which
resolves its one dependency (`mcp`) on first launch.

**Prerequisites:** `uv` on PATH, SSH access to Unity under the `unity` host
alias, and a `.env` in your project (generated by `/unity-hpc:setup` into
`unityHPC/.env`).

Run Claude Code from your project directory — the MCP server reads campaign
state from the working directory unless `PROJECT_DIR` is set.

## The job lifecycle

One contract ties the whole plugin together: **`unityHPC/run.sh` records every
job it submits, and every management tool reads that record.**

```
run.sh run <exp>  ──sbatch──►  SLURM
       │                          │
       └── writes ────►  .unity_state/<campaign>.db   ◄── shared telemetry
                                  │                       (collector, ~15 min)
        ┌─────────────────────────┴─────────────────────────┐
   unity_status / unity_jobs / unity_my_jobs        run.sh status  (live sacct)
   unity_logs / unity_results                       run.sh logs / fetch
```

| Command | Talks to the cluster? | Use it for |
|---|---|---|
| `run.sh run <exp> [--campaign N] [--dry-run]` | yes | submit, and record the job |
| `run.sh jobs` | no | what this project has submitted |
| `run.sh status` | yes (one `sacct`) | live state, written back to the ledger |
| `run.sh logs [-n N]` | yes | tail the newest job's output |
| `run.sh fetch` | yes (`rsync`) | pull this campaign's `.out`/`.err` + artifacts |
| `run.sh render <exp>` | no | preview the sbatch script |
| `run.sh sync` | yes (`rsync`) | push the project to `$REMOTE_DIR` |

Any of `JOB_COMMAND`, `WALLTIME`, `SLURM_{PARTITION,CPUS,MEM,NODES,GPUS,GPU_TYPE,ACCOUNT}`,
`REMOTE_DIR`, `UNITY_HOST`, `CAMPAIGN`, `MODULES`, `VENV_PATH`, `HF_HOME` and
`USER_EMAIL` can be overridden for a single invocation
without editing `.env` — the caller's environment wins:

```bash
JOB_COMMAND="echo smoke-test" SLURM_MEM=1G SLURM_PARTITION=cpu bash unityHPC/run.sh run smoke
```

That is how you smoke-test a project whose real job is a four-hour GPU run, and
how you resize one retry without disturbing every other run.

A **campaign** is just a label grouping submissions; it defaults to today's UTC
date. Nothing runs in the background — there is no monitor process, nothing
auto-fetches, and nothing auto-requeues. The ledger is local-only (`sync.sh`
excludes it) and is upgraded in place when a new plugin version adds a column.

Jobs submitted with bare `sbatch`, outside `run.sh`, are invisible to all of the
above — that is the one thing the abstraction cannot do for you.

## Metrics are declared, never assumed

The plugin serves every kind of SLURM job, so its core names **no** metric.
`unity_results` reports the `key: value` numeric lines each job printed, in the
order it found them, and ranks nothing.

A project with a headline metric opts in with `unityHPC/metrics.json`:

```json
{
  "primary": "val_bpb",
  "goal": "min",
  "report": ["val_bpb", "peak_vram_mb", "mfu_percent"],
  "labels": {"peak_vram_mb": "vram_mb"}
}
```

| Field | Effect | Omitted |
|---|---|---|
| `primary` + `goal` (`min`/`max`) | names the best job | nothing is ranked |
| `report` | puts these columns first | discovery order |
| `labels` | display-only renaming | raw key names |

Metrics a job prints but does not declare are still shown — hiding real output
would make the report lie. Declared metrics that no job printed are called out
explicitly, which is usually how you learn a run died early. A malformed
declaration degrades to the generic view and says why. `tests/test_contract.py`
fails if any metric name reappears in `mcp/` or `lib/`.

## `hardware` is a device, not a queue

`task_run.hardware` records what a job **ran on** — a GPU type (`a100`,
`titan_x`), `gpu:unspecified` when it held a GPU sacct did not name, or `cpu`.
The queue lives in its own `task_run.partition` column.

It used to fall back to the partition string whenever the GPU type was unknown,
so one column mixed two taxonomies: `a100` (a device) sat beside `gpu-preempt`
and `gpu,gpu-preempt` (queues, which were often a100s themselves). Anything
ranking by hardware — `task_profile`, `recommend-hardware` — was comparing
buckets that were not comparable. 84 distinct values collapsed to 17 once
repaired, and 22,070 jobs filed under `gpu` turned out to be a100s.

`cluster-intel/backfill_hardware.py` repairs an existing store. It re-derives
every row from the raw telemetry rather than guessing, leaves rows with no raw
record untouched, reports the counts, and is safe to re-run.

## When behaviour disagrees with the source

Call `mcp__unity-hpc__unity_doctor`. The MCP server loads once per session, so a
plugin upgrade mid-session leaves the process serving the *old* code while the
files on disk show the fix — indistinguishable from a bug until you ask the
running process what it is. `unity_doctor` reports its own version and source
path, flags code replaced after start or a version mismatch against
`installed_plugins.json`, and shows scaffold/ledger/metric/shared-data state.
The cure is `/reload-plugins` or a session restart.

One case it cannot report on itself: a server predating 0.8.0 has no
`unity_doctor` at all. If the tool is missing or answers `Unknown tool`, that
*is* the diagnosis — the session is running a pre-0.8.0 server and needs a
reload.

## Analysis dependencies (only for cluster-intel scripts)

The MCP server needs nothing beyond `mcp`. The `cluster-intel/*.py` scripts and
`scripts/hpc-usage` need heavier libraries:

```bash
uv pip install -r mcp/requirements.txt
```

## Skills

| Skill | Purpose |
|---|---|
| `/unity-hpc:setup` | Bootstrap a project — pick cpu/gpu/ml, generate `unityHPC/`, verify SSH, sync |
| `/unity-hpc:run <exp>` | Submit one job to SLURM (queue-aware, any job type) |
| `/unity-hpc:sweep` | Submit a batch of related jobs under one campaign |
| `/unity-hpc:status` | Check job states (instant local read; live check on request) |
| `/unity-hpc:fetch` | Retrieve job output and artifacts from the cluster |
| `/unity-hpc:resume` | Rebuild context after session reset |
| `/unity-hpc:log-result` | Record experiment to results.tsv |
| `/unity-hpc:recon` | Profile cluster — limits, partitions, GPU types, sacct scope, capacity |
| `/unity-hpc:recommend-hardware` | Rank GPU backends by your measured speed vs availability |

## cluster-intel — usage history & analysis

Authoritative, cluster-wide usage history from `sacct` + queue/GPU telemetry,
rolled up into `summaries.db`.

| File | Runs on | Purpose |
|---|---|---|
| `collector.sh` | cluster (tmux, singleton) | Sole cluster-side writer — samples partitions/nodes/GPUs/queue/jobs every 15 min → `telemetry/*.jsonl`; owns the 35-day retention prune |
| `sync-telemetry.sh` (`hpc-sync-telemetry`) | local | Locked, retention-aware pull of `telemetry/` into the shared data dir |
| `rollup.py` | local | Summarizes raw telemetry into `summaries.db` (`hourly_resource`, `daily_resource`, `task_profile`) |
| `cluster-config.json` | local (shared) | Cluster limits/GPU types/capacity from `unity-hpc:recon` — one shared copy for all projects, merge-written |

**Shared data location.** All local cluster-intel data (`cluster-config.json`,
`summaries.db`, `telemetry/`) lives in a single machine-wide
dir shared by every project and **kept outside the versioned plugin install** so
it survives plugin updates:

```
$UNITY_HPC_DATA        (default ~/.local/share/unity-hpc, honors $XDG_DATA_HOME)
├── cluster-config.json written by unity-hpc:recon
├── summaries.db        hourly_resource, daily_resource, task_profile (rollup.py)
├── telemetry/          synced raw collector output (hpc-sync-telemetry)
└── archive/            pre-redesign snapshot, read-only (dashboard only)
```

The plugin *code* is the versioned shared install (`${CLAUDE_PLUGIN_ROOT}`); the plugin
*data* is this dir. Every script/tool defaults to it and honors `$UNITY_HPC_DATA`.
