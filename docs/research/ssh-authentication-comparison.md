# SSH authentication for Unity: T3 Code and OpenSSH

Research checked 2026-10-02. The T3 Code observations below use [commit `8ed276c`](https://github.com/pingdotgg/t3code/tree/8ed276c246b624631e7d39241ebfd22d8314cb68).

## What T3 Code does

T3 Code's desktop SSH environment uses the installed `ssh` client and accepts an SSH host alias. It starts or reuses a remote server and forwards a local port; the remote project and provider credentials stay on that host. [T3 Code remote access guide](https://github.com/pingdotgg/t3code/blob/8ed276c246b624631e7d39241ebfd22d8314cb68/docs/user/remote-access.md#desktop-managed-ssh), [SSH command construction](https://github.com/pingdotgg/t3code/blob/8ed276c246b624631e7d39241ebfd22d8314cb68/packages/ssh/src/command.ts#L101-L112).

When the desktop detects an SSH authentication failure, it asks for a password, retries, and caches that string in a `Map` owned by its SSH environment manager. The cache is process memory, with no disk persistence in this path. Its `SSH_ASKPASS` helper supplies the cached string to a child `ssh` process through `T3_SSH_AUTH_SECRET` in the child environment. That string can be an SSH account password or a private-key passphrase, depending on what the SSH client asked for; the UI prompt calls it an SSH password. This approach is **not** a hardware passkey manager or a durable keyring. A T3 Code process restart, changed server policy, revoked key, or incorrect public key can still require action. [Manager cache and retry](https://github.com/pingdotgg/t3code/blob/8ed276c246b624631e7d39241ebfd22d8314cb68/packages/ssh/src/tunnel.ts#L1326-L1488), [askpass helper and child environment](https://github.com/pingdotgg/t3code/blob/8ed276c246b624631e7d39241ebfd22d8314cb68/packages/ssh/src/auth.ts#L72-L85), [environment setup](https://github.com/pingdotgg/t3code/blob/8ed276c246b624631e7d39241ebfd22d8314cb68/packages/ssh/src/auth.ts#L173-L202). The conclusion about no disk persistence is limited to this SSH implementation; T3 Connect has a separate account and pairing flow. [T3 Code remote access guide](https://github.com/pingdotgg/t3code/blob/8ed276c246b624631e7d39241ebfd22d8314cb68/docs/user/remote-access.md).

Its transport settings are separate from authentication: the SSH command has a 10-second connection timeout, while the forwarded tunnel sets `ServerAliveInterval=15` and `ServerAliveCountMax=3`. These detect or bound a broken connection; they do not authorize a rejected key. [Command options](https://github.com/pingdotgg/t3code/blob/8ed276c246b624631e7d39241ebfd22d8314cb68/packages/ssh/src/command.ts#L101-L112), [tunnel options](https://github.com/pingdotgg/t3code/blob/8ed276c246b624631e7d39241ebfd22d8314cb68/packages/ssh/src/tunnel.ts#L1137-L1157).

## What Unity requires

Unity's current SSH guide specifies `login.unityhpc.org`, a portal username in the form `username_school_edu`, and an `IdentityFile` pointing to the private key whose public half is in the Unity account. Its troubleshooting guide says `Permission denied (publickey)` can result when the client and Unity cannot match the keys; it also names PI endorsement and a valid login shell as account checks. The reported hostname `unity.rc.umass.edu` differs from Unity's documented general login hostname, so verify its intended role. [Unity SSH guide](https://docs.unity.rc.umass.edu/documentation/connecting/ssh/), [Unity troubleshooting](https://docs.unity.rc.umass.edu/documentation/help/troubleshooting/).

**Local diagnosis supplied by the project review:** `ssh -vv` in batch mode offered the configured encrypted Ed25519 key, and Unity replied `Server accepts key`. The client then failed because the selected SSH agent had no loaded signer; the controller was using a different agent socket. This direct trace narrows this incident to local key unlocking/agent selection. The final `Permission denied (publickey,hostbased)` line does **not** prove Unity rejected the public key. The machine has GNOME Keyring Secret Service and `kwalletd6`, but `gcr-ssh-agent.socket` is disabled, `ksshaskpass` is absent, and `gpg-agent-ssh.socket` is active. These are local observations, separate from the external sources above.

Unity recommends a passphrase-protected private key and an SSH agent, which keeps unlocked keys in memory so repeated SSH connections do not ask for the passphrase. OpenSSH's `AddKeysToAgent yes` can load a file key into the running agent after one successful passphrase entry, and `IdentityFile` with `IdentitiesOnly yes` selects the intended key even when the agent holds many. `ssh-agent` is a process: its key cache is not itself persistent across reboot or agent restart. A lifetime configured by `ssh-add -t`, `ssh-agent -t`, or `AddKeysToAgent` can remove a key sooner. [Unity SSH guide](https://docs.unity.rc.umass.edu/documentation/connecting/ssh/), [OpenSSH ssh_config](https://man.openbsd.org/ssh_config), [OpenSSH ssh-agent](https://man.openbsd.org/ssh-agent), [OpenSSH ssh-add](https://man.openbsd.org/ssh-add).

An OpenSSH FIDO security key is another kind of credential. Its hardware protects a key used for SSH signatures, and normal use requires the authenticator to be present and usually touched. A PIN or verification requirement can add another prompt. It therefore does not satisfy literal unattended, zero-prompt reconnection. Whether Unity accepts a `*-sk` public key should be verified with Unity before choosing one; its SSH setup guide currently describes portal-generated RSA keys. [OpenSSH ssh-keygen](https://man.openbsd.org/ssh-keygen), [Unity SSH guide](https://docs.unity.rc.umass.edu/documentation/connecting/ssh/).

For persistence across agent restarts, use the desktop's encrypted secret store rather than a custom repo secret file. KDE's `ksshaskpass` is an SSH askpass helper that saves a key passphrase through QtKeychain when the user chooses to keep it; the default KWallet can open on desktop login when `kwallet_pam` is installed and configured. [KDE ksshaskpass README](https://github.com/KDE/ksshaskpass), [KDE ksshaskpass source](https://github.com/KDE/ksshaskpass/blob/master/src/main.cpp), [KWallet handbook](https://docs.kde.org/stable_kf6/en/kwalletmanager/kwalletmanager/introduction.html). On GNOME, GCR's SSH agent can retrieve saved key passphrases from GNOME Keyring, as its maintainer describes; GNOME stores keyring credentials in an encrypted local file. These are **desktop-session integrations**: a locked wallet/keyring, missing login integration, or unattended reboot without desktop login can still block signing. [GNOME GCR maintainer explanation](https://discourse.gnome.org/t/gdm-gnome-keyring-and-gcr-ssh-agent-service/23498/3), [GNOME system guide](https://help.gnome.org/system-admin-guide/processes.html), [GNOME keyring unlock guide](https://help.gnome.org/seahorse/keyring-unlock.html).

The existing GNOME Keyring Secret Service also exposes libsecret storage through `secret-tool`. Its secret lookup may unlock a locked collection, so an unattended service cannot count on retrieval before the desktop keyring is open. Its lookup attributes are **not encrypted**; use them only for nonsensitive identification, not the passphrase. `secret-tool lookup` writes the secret to stdout, so any integration must keep that stream out of logs, shell tracing, environment variables, and command arguments. [GNOME libsecret API](https://gnome.pages.gitlab.gnome.org/libsecret/libsecret-simple-api.html), [secret-tool manual](https://manpages.debian.org/unstable/libsecret-tools/secret-tool.1.en.html).

## Integration direction for this repository

The [architecture](../../ARCHITECTURE.md) puts SSH/rsync in the local controller; the agent-facing skills call the controller over HTTP. Keep this split. Use the system OpenSSH client and one explicit `Host unity` profile, with Unity's documented hostname and the exact enrolled key. Confirm `ssh -G unity` resolves the expected host, user, and identity; confirm the key matches the portal before changing cache behavior. Unity's troubleshooting guide recommends `ssh -i <key>` to separate a key problem from SSH config selection. [Unity troubleshooting](https://docs.unity.rc.umass.edu/documentation/help/troubleshooting/), [Unity SSH guide](https://docs.unity.rc.umass.edu/documentation/connecting/ssh/).

For repeated jobs in one login session, let a user-managed `ssh-agent` hold the unlocked key; controller subprocesses must use the **same** `SSH_AUTH_SOCK` as the working interactive shell. In this incident, fixing that mismatch and loading the already accepted key is the immediate path to recovery. `BatchMode=yes` makes unattended jobs fail quickly and clearly if authorization is unavailable. Set bounded connection and command timeouts separately from keepalives. For *across-reboot* convenience, use a desktop keyring integration after sign-in; plain OpenSSH agent caching alone cannot make a one-time passphrase entry last forever. Do not put a passphrase in this repository, a project `.env`, a command argument, or controller logs. T3 Code's process-environment askpass pattern is not a sound durable secret store to copy into an always-on controller. [OpenSSH ssh_config](https://man.openbsd.org/ssh_config), [OpenSSH ssh-agent](https://man.openbsd.org/ssh-agent), [T3 Code askpass implementation](https://github.com/pingdotgg/t3code/blob/8ed276c246b624631e7d39241ebfd22d8314cb68/packages/ssh/src/auth.ts#L72-L85).

No client-side design can guarantee access forever: Unity may remove an enrolled key, disable an account, or change server policy. A passphrase cache only solves repeated **local key unlocking**. `Permission denied` after a key is offered requires checking the server-side key and account; keepalives only address dropped **connections**. [Unity troubleshooting](https://docs.unity.rc.umass.edu/documentation/help/troubleshooting/), [OpenSSH ssh-agent](https://man.openbsd.org/ssh-agent), [OpenSSH ssh_config](https://man.openbsd.org/ssh_config).
